### WP1. 비교 프로토콜 정리 · 4–6시간 · 최우선

목적: "논문을 이겼다"를 "명시한 입력 조건에서 이 오차로 복원했다"로 바꿉니다. 비용이 가장 낮고 근거 없는 주장을 먼저 제거합니다.

1. `real_benchmark.py`에 **같은 시행·같은 초기화·같은 제외 규칙**의 기준선 두 개를 추가합니다. (가) 시행별 단순 감속 μ의 중앙값, (나) 물체별 평균. Tether와 한 표에 둡니다.
2. **시행 하나씩 빼고 보정해 빠진 시행의 정지 위치를 예측**하는 평가를 추가합니다. val/test 분할은 크래커 상자에 val이 없어 쓸 수 없습니다. 지표는 정지 위치 오차의 중앙값과 90분위(cm)이고, 시행이 하나뿐인 경우는 "평가 불가"로 표시합니다.
3. 결과 JSON에 `excluded`(사유별 제외 수)와 `inputs`(데이터셋 보정값, 모션캡처로 정한 추적 시작점, 모션캡처 물체 높이)를 추가하고, README 표 바로 아래에 같은 내용을 한 문단으로 둡니다.
4. 논문 0.082는 "참고 (다른 프로토콜: RGB-D 온라인 추적·필터링)" 한 줄로 분리합니다. 수정 대상: README, DEVPOST, `submission/about-the-project.md`, 기사 ko/en, `docs/guide/00·04`, STATUS, `film/stage.html:223`, `film/render.py:111`.
5. `test_docs_numbers.py`의 실측 표 테스트를 새 표에 맞추고, 0.082가 나오는 모든 문장에 프로토콜 표기가 붙었는지 검사합니다.
6. `make film` → `make submission`으로 영상과 업로드 폴더를 다시 만듭니다.

완료 기준: `make real-benchmark` 재실행 결과가 JSON·README·DEVPOST에 일치하고, Tether와 기준선이 같은 시행에서 나란히 보이며, 제외 20/45가 문서에 있습니다. 이긴다는 보장은 없습니다. 기준선과 비슷하면 그대로 씁니다.

### WP2. 믿을 수 있는지 알려주는 상태 표시 · 8–10시간

목적: Tether를 "숫자를 추정하는 도구"에서 "언제 그 숫자를 믿으면 안 되는지도 알려주는 도구"로 만듭니다.

0. **먼저 원인을 진단합니다** (`overnight-harness:diagnose`, 1–2시간). 크래커 상자가 모든 경로에서 빗나가는 이유를 증거로 확인합니다(키 큰 상자의 쏠림·회전, 추적, 기울기 시험값 자체). 시행별 단순 감속 μ의 흩어짐이 신호가 되는지 봅니다. 그 결과로 상태 판정에 쓸 신호를 정합니다.
1. `tether/studio/reliability.py`: 순수 함수 `assess(session, cal)`이 `level`(ok / limited / unreliable)과 `reasons`를 돌려줍니다. 이유는 코드+매개변수(`few_pushes`, `unexplained_pattern`, `unmeasured_range` 등)이며, 문구는 화면에서 만듭니다.
2. 시행이 너무 적어 부트스트랩이 의미 없는 경우(1개)에는 **구간을 숨깁니다**. 그 위 단계의 시행 수 기준은 제품 정책값입니다. 근거로 시행 수별 포함률을 EV-RealPhys 부분표본과 교차 엔진 24개 세계에서 측정하되, 통계적 기준처럼 쓰지 않습니다.
3. **파라미터 구간과 예측 구간을 분리**합니다. `predict_stop(cal, launch_speed)`가 앙상블과 잔차 잡음으로 정지 위치의 중앙값과 90% 범위를 돌려줍니다. "Where it stops" 곡선에는 파라미터 띠와 예측 띠를 다른 농도로 겹치고, 범례에 한 줄로 설명합니다.
4. UI는 결과 상단에 **상태 칩 하나**(색 + 한 문장)를 두고 이유는 접어 둡니다. 보고서·JSON·Newton/Isaac 스니펫 머리말에도 같은 상태를 담습니다. 영어·한국어 문구를 모두 쓰고 `test_i18n.py`로 누락을 막으며, 데스크톱과 390 px 캡처(영어·한국어)로 확인합니다.
5. 평가: EV-RealPhys 10개 사례(물체 5 × 경로 2)에서 (가) 오차가 0.05를 넘는 사례가 경고 상태인지, (나) 경고가 없는 사례의 포함률이 얼마인지를 표로 공개합니다. 경고가 안 걸리면 숨기지 않고 "이 신호로는 잡지 못함"으로 기록합니다.

판단 시점: 경고가 없는 사례에서도 포함률이 90%에서 크게 벗어나면, 구간에 측정 모델 오차의 하한폭을 넣을지 별도로 결정합니다. 지금은 계산식을 바꾸지 않습니다.

완료 기준: 시행 1개짜리 보정은 구간 대신 "측정 부족"을 보여주고, 상태가 UI·보고서·JSON에 일관되게 나옵니다. 위 5번의 표가 README에 있습니다.

### WP3. Export를 파일 기준으로 한 경로 끝까지 검증 · 6–8시간

목적: "보정 → 파일 생성 → 별도 프로세스에서 파일 로드 → 새 시행 실행 → 결과 비교"를 **Newton에서** 완성합니다. Isaac Lab·CARLA는 이 환경에서 실행할 수 없으므로(NVIDIA GPU 장비 필요) 검증 수준을 구분해 표시합니다.

1. **Isaac Lab 재질 수정을 가장 먼저** (작은 버그입니다). 표면 재질을 `MU_EFF`로 고정하고 물체 범위를 `(2·lo − MU_EFF, 2·hi − MU_EFF)`로 바꿔, 평균 결합에서 유효 마찰이 `[lo, hi]`가 되게 합니다. 음수는 0으로 자르고 머리말에 산식을 적습니다. 반영 전에 Isaac Lab 문서에서 기본 결합 방식과 `randomize_rigid_body_material`의 인자를 확인합니다. 기존 테스트의 `EventTerm(` 개수 단언(`tests/test_studio_api.py:40`)이 바뀝니다.
2. `calibration.json`에 앙상블(최대 30개)을 추가하고, Isaac 스니펫 머리말에 "변수별 범위이며 조합이 아님"을 적습니다.
3. `tether/studio/roundtrip.py`와 CLI(`python -m tether.studio replay EXPORT_DIR ...`): `calibration.json`을 읽어 기본 단위의 `ParamSet`을 만들고(도메인 배율 포함), **별도 프로세스**에서 `NewtonPushEnv`로 새 시행을 실행해 정지 위치를 비교합니다. `newton_calibration.py`의 상수(`MU_EFF` 등)를 `ast`로 읽어 JSON과 일치하는지도 확인합니다.
4. `verify`를 두 모드로 나눕니다. 시행이 충분하면 일부를 빼고 재보정해 **새 시행 예측 오차**를 보여주고, 부족하면 지금처럼 하되 문구를 "학습에 쓴 시행의 재현"으로 바꿉니다. 구체적인 기준 시행 수는 정책값입니다.
5. 내보내기 탭에 한 줄로 표기합니다: Newton은 "실행 검증", Isaac Lab·CARLA는 "형식 검증 (스탠드인 모듈, 이 환경에서 실행하지 않음)". README도 같게 맞춥니다.

완료 기준: `tests/test_roundtrip.py`(Newton 표시)가 파일 → 새 프로세스 → 새 시행 재현을 통과합니다. Isaac 스니펫은 스탠드인 모듈 테스트로 유효 마찰 범위가 보정 구간과 같음을 확인합니다(기존 CARLA 테스트와 같은 방식). 로봇·주행(배율 있음) 두 도메인을 모두 다룹니다.

### WP4. Nemotron의 기여 분리 · 4–6시간

목적: LLM이 최종 결과에 기여한 부분과 안전장치가 기여한 부분을 분리해 포지셔닝을 정합니다.

- 세 조건: **(a) 비LLM 구조 탐색 / (b) Nemotron 단독 / (c) Nemotron + 교차 검증**. (b)와 (c)는 같은 에이전트 호출을 공유합니다. 교차 검증은 사후 단계이므로 호출 1번으로 둘을 모두 얻습니다. `pipeline.analyze`에 교차 검증을 끄는 스위치만 추가합니다.
- 데이터: 교차 엔진 24개 세계 + Newton 예시 6개 + EV-RealPhys 기록 경로 5개. 동일한 데이터와 추가 시행 예산입니다.
- 지표: 보류한 시행의 정지 위치 오차, 구조 선택 정확도(정답이 있는 세계), 실패율, 지연 시간, 비용, **교차 검증이 에이전트 결과를 뒤집은 횟수**.
- 비용: 호출당 약 $0.0013(Super)이므로 약 35개 세계에서 $0.1 안팎입니다. 응답은 `RecordedLLM` 기록으로 저장해 이후 `make check`에서 오프라인으로 재생합니다. 실제 호출은 한 번만, 사용자 승인 후 실행합니다.
- 해석 규칙은 미리 정합니다. (c)가 (a)와 신뢰구간 안에서 같으면 포지셔닝을 "모델 후보를 검토하고 다음 실험을 정하도록 안내하는 보정 에이전트"로 쓰고, 정확도 우위를 말하지 않습니다. 교차 검증이 뒤집은 사례가 있으면 그 수를 안전장치의 가치로 제시합니다.
- 사용자 3–5명이 결과를 해석하고 다음 실험을 고르는 15분 과제는 **선택 사항**입니다. 사람이 없으면 "사용자 시험을 하지 않았음"이라고 적습니다.

### WP5. 독립 스마트폰 사례 한 건 · 도구 2–3시간 + 촬영 1–2시간

1. `prove_real.py`에 보정/평가 분리를 추가합니다. 한 물체-표면 쌍에서 앞의 시행으로 보정하고 나머지 시행의 정지 위치를 측정한 출발 속도로 예측해 비교합니다. 평가용 시행의 최종 위치는 보정에 쓰지 않으며, 추적에 실패한 시행도 사유와 함께 표에 남깁니다. 결과에 WP3의 파일 왕복 재현도 붙입니다. `docs/guide/06`은 쌍당 15번(보정 10 + 평가 5)으로 바꿉니다. 이는 소규모 검증 설계이고 통계적으로 충분한 표본 수라는 뜻이 아닙니다.
2. [사용자] 휴대폰 + A4로 1쌍 이상 촬영하고 기울기 앱으로 각도를 잽니다. 가능하면 3쌍이 좋습니다(`make prove-real`). 영상 원본은 `film/real/`(git 무시)에 두고 숫자만 커밋합니다.
3. 촬영이 어렵다면 WP1의 시행 단위 평가가 대체 근거입니다. 제품 사용성을 입증하는 데는 새 사례가 더 직접적입니다.

### WP6. 메시지·글·데모 정리 · 4–6시간 (WP1–4의 숫자 확정 후)

1. 한 줄 소개로 통일: "Tether는 밀기 작업의 영상·로그에서 시뮬레이터의 물리 차이를 추정하고, 아직 모르는 구간을 드러내며, 다음 실험과 검증 가능한 설정을 제공하는 도구입니다." 영어판도 같은 의미로 씁니다. 적용 대상은 README 첫머리, Overview 첫 화면, DEVPOST, 기사, YouTube 설명입니다.
2. 대표 사례는 **로봇·제조의 밀기 작업**입니다. 차량 제동은 "같은 모델을 배율로 확장한 예"로 뒤에 둡니다. 기능은 지우지 않고 순서와 문구만 바꿉니다.
3. 기사 첫머리는 "입력 영상 → 보정 결과 → 평가에 쓰지 않은 시행의 예측"을 먼저 보여주고(WP1·WP5의 결과), 구현 설명은 그 뒤에 둡니다.
4. 용어: 시뮬레이션을 가리키는 "숨겨진 실제 환경"은 "숨겨진 시뮬레이션 환경"으로 바꿉니다. 코드의 `real` 이름은 그대로 두고, 공개 문서에 옛 표현이 남지 않도록 검사하는 테스트를 추가합니다.
5. 표와 그림마다 데이터 출처를 네 가지로 표기합니다: **Newton 합성 / MuJoCo 교차 엔진 / 공개 실측(EV-RealPhys, IDPP) / 직접 촬영**. 같은 자리에서 "이번에 다시 계산한 값"과 "기존 기록을 인용한 값"도 구분합니다.
6. 포트폴리오 사본(`men16922.github.io/public/posts/tether/`)을 같은 내용으로 맞춥니다. 외부 공개 변경이라 푸시 전에 확인합니다.

### WP7. 제출과 심사 기간 운영 · 1–2시간 + 사용자 확인

1. `make presubmit`을 추가합니다. `make check`, 문서 수치 대조, `YOUTUBE_LINK` 등 자리표시자 검색, 링크 목록 출력을 한 번에 합니다. 10-28에 사용합니다.
2. 규정 확인 목록(원문은 사용자가 다시 읽습니다): 3분 미만의 공개 YouTube 영상(현재 2:28), 핵심 모듈이 동작하는 장면 1분 이상(현재 약 68초), Token Factory 추론 호출이 Nebius 사용으로 인정되는지.
3. 심사 기간(12-01 ~ 12-15) 운영: Cloud Run은 인스턴스 최대 1개와 0까지 축소 설정이 이미 되어 있습니다. [사용자] Token Factory 키와 크레딧이 12-15까지 유효한지 콘솔에서 확인합니다. 라이브 데모가 내려가도 `make serve`와 standalone 페이지로 재현할 수 있다는 안내를 DEVPOST에 넣습니다.
4. 마지막 `make deploy` 후 라이브 주소에서 페이지·분석·내보내기를 확인합니다.
